Developer documentation

How FerriteGismo plugs a G+Smo spline discretization into Ferrite, for contributors.

Warning

FerriteGismo depends on a number of internal Ferrite functions, which makes it sensitive to Ferrite releases. The custom IGADofHandler in particular is a candidate for a redesign.

Design overview

Ferrite's assembly loop, iterators, cell values and solvers are reused unchanged; only the pieces specific to the geometry are replaced:

ConceptFerriteFerriteGismo
GeometryNodes + Lagrange cellsG+Smo geometry (control points)
GridGridIGAGrid
CellQuadrilateral, …IGACell (one per knot span)
InterpolationLagrange, …IGAInterpolation
Dof distributionDofHandlerIGADofHandler

The backend (knot vectors, basis evaluation, geometry, refinement, …) is provided by TinyGismo.jl, a Julian wrapper around the G+Smo C++ library. FerriteGismo re-exports both Ferrite and TinyGismo.

Grid and cells

An IGAGrid stores the G+Smo geometry, the control points as Ferrite Nodes, one FerriteGismo.IGACell per non-empty knot span, and a cached FerriteGismo.KnotSpanWrapper for each knot span. Each cell holds the indices of the basis functions that are active on its knot span; these take the role of the cell "nodes" and are the basis for the connectivity used during assembly.

The reference dimension rdim (parametric dimension) and spatial dimension sdim are kept as separate type parameters so that embedded geometries (rdim < sdim) can be represented, even though not all code paths support them yet.

FerriteGismo.IGACell — Type
IGACell{rdim} <: Ferrite.AbstractCell{Ferrite.RefHypercube{rdim}}

Internal cell type of an IGAGrid, representing one knot span (Bézier element) of reference dimension rdim. Its nodes field stores the global indices of the spline basis functions that are active on the knot span; these play the role of the cell's "nodes" in the Ferrite sense and are what celldofs are derived from.

source
FerriteGismo.KnotSpanWrapper — Type
KnotSpanWrapper{dim}

Internal, immutable description of a single knot span (Bézier element) of a tensor-product spline basis. It caches the center, lower and upper corner of the knot span in parameter space as Vec{dim} values, converted once from the underlying TinyGismo.KnotSpan.

KnotSpanWrappers back the cells of an IGAGrid and are used during reinit! to remap quadrature points to parameter space (via FerriteGismo.ref_to_param) before an IGAInterpolation evaluates them, and to compute knot-span areas.

The export mesh

For visualization and for evaluating solutions at grid nodes, FerriteGismo builds an ordinary Ferrite grid over the knot spans: exportGrid places its nodes at the physical positions of the knot-span corners, parameterSpaceGrid is the same mesh with parametric coordinates, and exportPoints are those coordinates as a plain vector. All three are derived from breakpoints, which reads the knot-span boundaries per direction, so the mesh follows the actual (possibly non-uniform) knots.

A subdivision keyword samples every knot span several times per direction, which is how a curved geometry or a high-order field is resolved in the picture.

Interpolations

IGAInterpolation is a Ferrite.ScalarInterpolation wrapping a G+Smo basis. Unlike a Lagrange interpolation, its active basis functions depend on the knot span. The interpolation stays stateless: reinit! maps the quadrature points into the current knot span (FerriteGismo.ref_to_param) before the basis is evaluated through:

  • Ferrite.reference_shape_values!
  • Ferrite.reference_shape_gradients_and_values!
  • Ferrite.reference_shape_hessians_gradients_and_values!

Geometry mapping

FerriteGismo.IGAMapping specializes Ferrite.calculate_mapping and Ferrite.apply_mapping! to compute the Jacobian (and the Hessian where available) and push the gradients to physical space. Since the Jacobian is taken with respect to the parametric coordinates, detJdV is additionally scaled by the knot-span area relative to the reference element.

Facet values

Ferrite.reinit!(::FacetValues, ::CellCache, facet_nr) works like the cell version, with the weights scaled by the knot-span length along the facet (FerriteGismo.facetScaleOfKnotSpan). Facet sets are computed on demand from the knot-span corners by Ferrite.getfacetset(::IGAGrid, name).

Degree-of-freedom handling

The IGADofHandler wraps a Ferrite.DofHandler and forwards most calls to it, but owns its SubDofHandlers so that sdh.dh is the IGA handler. close! numbers the dofs by control point rather than by Lagrange node: each field gets one global block, shared by all subdofhandlers, with the components interleaved per control point. Several subdofhandlers are only needed on hierarchical patches, where they group elements by active-function count.

allocate_matrix builds the sparsity pattern from the cell dofs itself, since Ferrite's version is typed on the concrete DofHandler. The CellCache/CellIterator methods in iterators.jl make Ferrite's iteration use the IGA connectivity.

Note

The implementation reaches into a number of DofHandler internals. A cleaner approach would be to generalize Ferrite's dof distribution rather than reimplement it here.

Boundary conditions

Neumann conditions need nothing special. Ferrite's Dirichlet on a facet set does not work, since it evaluates the condition at facet dof positions, which spline bases do not have. Instead conditions are put on the control points of a parametric side:

  • fixEdge! calls Ferrite.add_prescribed_dof! for the boundary control points.
  • prescribeEdge! and add!(ch, ::Dirichlet) on a set of control points store the condition like a Ferrite node-set condition, so update! computes the values.
  • The shell form of fixEdgeTangent! collects its conditions until close!(ch), where those meeting at a corner are combined into affine constraints.

Postprocessing and L2 projection

The export path stays on Ferrite's public API: the writers get the export mesh, a plain Ferrite Grid, and the spline fields are evaluated at its nodes with evaluateAtExportNodes. FerriteGismo only adds methods of public functions (VTKGridFile, write_solution, write_projection, evaluate_at_grid_nodes, L2Projector, project) for its own types.

The exact export, VTKBezierFile, cannot go through an export mesh: it writes the Bézier cells with WriteVTK directly. The extraction operator of each knot span is computed from G+Smo evaluations at points inside the span, which covers B-spline, NURBS and hierarchical bases alike. For the point data it reuses Ferrite._vtk_write_node_data, which converts tensors to their Paraview components.

The L2 projector assembles and factorizes the spline mass matrix once and solves for each tensor component. It subtypes the internal Ferrite.AbstractProjector so that code constrained on that type accepts it.

FerriteGismo.L2ProjectorIGA — Type
L2ProjectorIGA <: Ferrite.AbstractProjector

IGA counterpart of Ferrite's L2Projector, used to project (typically discontinuous) quadrature-point data such as stresses onto a continuous spline field for postprocessing and VTK export.

It is constructed through Ferrite.L2Projector(ip::IGAInterpolation, grid::IGAGrid) and stores the Cholesky factorization of the spline mass matrix together with an internal IGADofHandler carrying one scalar field, and the interpolations used to build it. Use project to obtain the projected control-point values, write_projection to export them and evaluate_at_grid_nodes to read them off the export mesh.

Contributing

Contributions are very welcome. Good starting points are:

  • reducing the reliance on internal Ferrite functionality,
  • redesigning the IGADofHandler,
  • improving boundary-condition support (a full ConstraintHandler integration),
  • adding tutorials and examples,
  • performance work and additional tests.
